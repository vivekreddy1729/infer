Deploying Carrier Policy Puller on AWS

ECS Fargate behind an Application Load Balancer, with EFS for persistent session state. Everything is AWS except the residential proxy, which is Proxy-Cheap.

Read the four constraints first

This app has requirements that rule out most of the obvious AWS choices, and two of them will cause failures that look like application bugs if you miss them. Each one below is a measured property of the app, not a preference.

1. What the app needs, and why

It runs a real, headed Chrome

GEICO's login endpoint POST /ws/login/authenticate returns 302 under headless and 200 headed — same machine, same IP, same browser binary. The single-page app cannot follow that redirect, so login stalls with no error. Measured, documented as F-40 in the engineering log.

So the container runs Chrome under Xvfb, a virtual framebuffer. It is a full windowed browser with no window anywhere and no X server needed on the host. The image's entrypoint does this automatically when HEADLESS=false.

Consequence: you need a container runtime with ~4GB RAM, not a function runtime.

Sessions live in memory, and a pull waits on a human

SessionManager holds live session objects, each owning an open browser context. The WebSocket carrying MFA state must return to the same container — there is no shared session store.

And MFA_WAIT_TIMEOUT_MS is 180 seconds, because a person has to read a text message and type a code. That single number invalidates several AWS defaults, most importantly the load balancer's.

State must survive a restart

/app/data holds AES-256-GCM encrypted storageState blobs, the metrics history, and rotating logs. Those blobs carry each carrier's trusted-device cookie, which is what lets a repeat pull skip the MFA challenge entirely. Lose the volume and every user is silently back to a full human round-trip on every pull.

Carrier traffic must egress from one residential IP

Handled by Proxy-Cheap, not AWS. What AWS must provide is plain outbound internet from the task so it can reach the proxy gateway. The task's own public IP is irrelevant to the carrier — all carrier traffic leaves through the proxy.

2. Why not Lambda, App Runner, or EKS

OptionWhy
Lambdano No Xvfb and no way to install it into the runtime. 15-minute ceiling is fine but there are no long-lived WebSocket connections, and session state would have to move to DynamoDB or ElastiCache — which cannot hold an open browser context at all.
App Runnerno Closest miss. It runs containers happily, but there is no EFS support, so there is nowhere to persist the encrypted session store, and no control over /dev/shm. Also no way to pin traffic to one instance.
EKSno It would work. A control plane costs $73/month before a single pod runs, to schedule one container that must not be replicated.
Elastic Beanstalkno Works, and wraps ECS in another abstraction whose defaults you then have to fight — particularly the load balancer idle timeout.
ECS Fargateuse this Containers, EFS, Secrets Manager, ALB, CloudWatch, no servers to patch. One caveat about /dev/shm below, which this app already handles.
ECS on EC2alternative Cheaper at this size and lets you raise /dev/shm. You patch the host. See section 9.

Fargate cannot raise /dev/shm — and this matters for Chrome

AWS's ECS documentation states plainly that for the Fargate launch type, the devices, sharedMemorySize and tmpfs parameters are not supported. You are stuck with the 64MB default, and docker-compose.yml's shm_size: 1gb has no Fargate equivalent.

Chrome normally crashes on content-heavy pages with 64MB of shared memory. This app survives because src/browser/stealth.js already passes --disable-dev-shm-usage, which makes Chrome write to /tmp instead.

That flag is therefore load-bearing on Fargate specifically. Removing it as a "cleanup" would work locally and in Docker Compose, and break in production only under load. If you want the shared memory instead, use ECS on EC2.

Stopping the clock

This is a demonstrable app, not a 24/7 service. aws ecs update-service --desired-count 0 stops Fargate billing within a minute and leaves EFS, the image and the secrets intact. Bringing it back is the same command with 1, and takes about 60 seconds. The ALB bills regardless — delete it too if you are pausing for weeks.

5. Deployment, step by step

Set these once for the whole session:

export AWS_REGION=us-east-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export APP=carrier-policy-puller
export ECR="$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$APP"
1

Build and push the image

Build for linux/amd64 explicitly. On an Apple Silicon Mac the default is arm64, and Fargate will pull an image it cannot execute — the task dies with exec format error, which reads like a corrupt image. 

aws ecr create-repository --repository-name $APP --region $AWS_REGION

aws ecr get-login-password --region $AWS_REGION \
  | docker login --username AWS --password-stdin "$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com"

docker buildx build --platform linux/amd64 -t "$ECR:latest" --push .
2

Store the secrets

The app refuses to boot in production without SESSION_ENCRYPTION_KEY. That is deliberate: without a stable key the session store is unreadable after every deploy, and every pull silently costs a human MFA round-trip. 

aws secretsmanager create-secret --name $APP/session-key \
  --secret-string "$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")"

aws secretsmanager create-secret --name $APP/diagnostics-token \
  --secret-string "$(node -e "console.log(require('crypto').randomBytes(24).toString('hex'))")"

# Proxy-Cheap: full URL including credentials, from your dashboard
aws secretsmanager create-secret --name $APP/proxy-url \
  --secret-string 'http://USER:PASS@gate.proxy-cheap.com:PORT'
3

Create the EFS filesystem and an access point

The access point is the part people skip, and then the mount is read-only. The container runs as pwuser — not root, confirmed in the Dockerfile — so without a POSIX-mapped access point EFS presents a root-owned filesystem and the app cannot write its session store. The symptom is subtle: the app starts fine and every pull just quietly asks for MFA again, because the session store is never written.

Check the uid before you set it — 1000 is conventional, not guaranteed

The Playwright base image conventionally gives pwuser uid 1000, and the commands below assume it. That was not verified while writing this document, so confirm it rather than trusting it — an access point mapped to the wrong uid produces exactly the silent unwritable-mount failure described above. 

docker run --rm --entrypoint id "$ECR:latest"
# uid=1000(pwuser) gid=1000(pwuser) ...  <- use these two numbers below
EFS_ID=$(aws efs create-file-system --encrypted \
  --tags Key=Name,Value=$APP --query FileSystemId --output text)

# One mount target per subnet the task runs in
aws efs create-mount-target --file-system-id $EFS_ID \
  --subnet-id subnet-AAA --security-groups sg-EFS

AP_ID=$(aws efs create-access-point --file-system-id $EFS_ID \
  --posix-user Uid=1000,Gid=1000 \
  --root-directory 'Path=/data,CreationInfo={OwnerUid=1000,OwnerGid=1000,Permissions=0700}' \
  --query AccessPointId --output text)

Confirm the uid if you have changed the base image:

docker run --rm --entrypoint id "$ECR:latest"

5

Create the load balancer — and change the idle timeout

This is the setting that will cost you an afternoon if you miss it.

ALB_ARN=$(aws elbv2 create-load-balancer --name $APP-alb \
  --subnets subnet-AAA subnet-BBB --security-groups sg-ALB --scheme internet-facing \
  --query 'LoadBalancers[0].LoadBalancerArn' --output text)

# THE CRITICAL LINE. Default is 60s; the app waits up to 180s for a human MFA code.
aws elbv2 modify-load-balancer-attributes --load-balancer-arn $ALB_ARN \
  --attributes Key=idle_timeout.timeout_seconds,Value=300

TG_ARN=$(aws elbv2 create-target-group --name $APP-tg \
  --protocol HTTP --port 3000 --vpc-id vpc-XXXX --target-type ip \
  --health-check-path /api/health --health-check-interval-seconds 30 \
  --healthy-threshold-count 2 --unhealthy-threshold-count 3 \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

aws elbv2 create-listener --load-balancer-arn $ALB_ARN \
  --protocol HTTPS --port 443 \
  --certificates CertificateArn=arn:aws:acm:REGION:ACCOUNT:certificate/XXXX \
  --default-actions Type=forward,TargetGroupArn=$TG_ARN

ALB idle timeout 60s vs MFA wait 180s

The WebSocket carrying MFA state is idle while the user reads a text message. At the default 60 seconds the ALB closes it mid-wait, and the failure presents as "the connection to this session is closed" or a silent timeout — pointing at the app, the browser, or the carrier. 300 seconds clears the 180-second wait with margin.

If you ever raise MFA_WAIT_TIMEOUT_MS, raise this with it. They are coupled and nothing enforces it.

6

Create the service with exactly one task

aws ecs create-service --cluster $APP-cluster --service-name $APP \
  --task-definition carrier-policy-puller --desired-count 1 --launch-type FARGATE \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-AAA,subnet-BBB],securityGroups=[sg-TASK],assignPublicIp=ENABLED}' \
  --load-balancers targetGroupArn=$TG_ARN,containerName=app,containerPort=3000 \
  --health-check-grace-period-seconds 120

desiredCount = 1 is a correctness requirement, not thrift

Sessions are held in an in-memory Map, each owning an open browser context. With two tasks, a user's WebSocket can land on the container that is not running their pull, and the MFA code goes nowhere — intermittently, and only under concurrency.

To scale beyond one task you need either ALB target-group stickiness with an application cookie, or to move session state out of process. Neither is done, and one task is the honest configuration for the current design.

Security groups and DNS

# ALB: public HTTPS in
aws ec2 authorize-security-group-ingress --group-id sg-ALB \
  --protocol tcp --port 443 --cidr 0.0.0.0/0

# Task: only from the ALB
aws ec2 authorize-security-group-ingress --group-id sg-TASK \
  --protocol tcp --port 3000 --source-group sg-ALB

# EFS: NFS only from the task
aws ec2 authorize-security-group-ingress --group-id sg-EFS \
  --protocol tcp --port 2049 --source-group sg-TASK

Then an alias A record in Route 53 pointing your hostname at the ALB.

6. Proxy-Cheap configuration

The only non-AWS component. Two settings, and one of them fails silently if it is wrong.

VariableWhereValue
RESIDENTIAL_PROXY_URLSecrets Managerhttp://USER:PASS@gate.proxy-cheap.com:PORT
PROXY_USERNAME_TEMPLATETask definition env{user}-session-{session} — verify this

A wrong sticky template does not error — it silently rotates

Residential gateways parse the proxy username, apply the flags they recognise, and ignore the rest. A wrong template therefore gives you a working proxy that changes IP on every connection. Login leaves from one address, the MFA submit from another, the document fetch from a third — and the carrier, seeing a session hop between cities, invalidates it. The error arrives as "your session expired", pointing three layers away from the cause.

Every provider spells stickiness differently and there is no standard. The template above is a starting guess: Proxy-Cheap's published API at docs.proxy-cheap.com is their ordering API — services, pricing, placing orders — and does not describe the connection protocol. Get the exact syntax from the dashboard.

Then prove it, locally, before deploying:

npm run proxy:verify

That holds one session for 45 seconds and requires the IP never to change — and separately requires a different session to get a different IP, which is what distinguishes working stickiness from an account that happens to have one static exit.

Pick a session lifetime longer than your worst-case pull. The app allows 180 seconds for a human to enter a code, so a 10-minute lifetime is a sensible floor. A one-minute lifetime will drop mid-flow.

The app pins the exit IP when a session opens and re-checks it before fetching documents. It cannot prevent a rotation — the IP belongs to someone's home connection — but it names one, which given the alternative attributions is most of the value.

7. Verifying the deployment

# 1. Is the task healthy?
aws ecs describe-services --cluster $APP-cluster --services $APP \
  --query 'services[0].{running:runningCount,desired:desiredCount,deployments:deployments[0].rolloutState}'

# 2. Does the app answer, and what did it load?
curl -s https://YOUR_DOMAIN/api/health | jq '{
  ok, uptimeSec,
  browser: .browser,
  headless: .config.headless,
  proxy: .proxy
}'

What to check in that response:

  • config.headless is false — otherwise GEICO will stall.
  • browser.channel — expect chromium from the Playwright image; chrome-headless-shell would mean the channel fallback degraded.
  • proxy.configured is true and proxy.stickyPlaceholderPresent is true. Note it reports stickyVerified: "unknown" by design — that is an empirical question, answered by npm run proxy:verify, not by a config file.
# 3. Does the WebSocket survive longer than the ALB default?
#    Open the app, start a DEMO MUTUAL pull, and leave the MFA prompt
#    untouched for 90 seconds before entering the code. If it completes,
#    the idle timeout is right.

# 4. End to end with no credentials
#    Pick "Demo Mutual (practice portal)" and run a pull. It exercises
#    login, the MFA round-trip, document fetch and PDF rendering.

The egress badge in the bottom-right of every page shows which IP carrier traffic is leaving from. Amber means no proxy; blue means proxied; green means a pull is running and that is the address the carrier is seeing right now.

Getting logs out

# CloudWatch (stdout/stderr)
aws logs tail /ecs/carrier-policy-puller --follow

# The app's own structured logs and failure bundles live on EFS, and include
# carrier API traces and diagnostic bundles CloudWatch does not have.

9. A cheaper single-EC2 alternative

If ~$92/month is more than this warrants, one t3.medium with an EBS volume and Caddy for TLS runs the same container for about $32/month. You give up managed TLS rotation, the ALB health-check loop, and painless host patching — and you gain the ability to set --shm-size properly. 

docker run -d --name puller --restart unless-stopped \
  -p 127.0.0.1:3000:3000 \
  --shm-size=1g \
  -v /srv/puller-data:/app/data \
  -e NODE_ENV=production -e HEADLESS=false \
  -e DATA_DIR=/app/data -e LOG_DIR=/app/data/logs \
  -e SESSION_ENCRYPTION_KEY=... \
  -e RESIDENTIAL_PROXY_URL=... \
  -e 'PROXY_USERNAME_TEMPLATE={user}-session-{session}' \
  "$ECR:latest"

Then Caddy in front, which gets you Let's Encrypt and correct WebSocket proxying in two lines — including a read timeout long enough for the MFA wait: 

your.domain {
  reverse_proxy 127.0.0.1:3000
}

Caddy's default timeouts do not cut idle WebSockets, so the ALB trap does not apply. Still set the security group to allow only 80 and 443 inbound.

Written against the app as of the current commit. The engineering log (docs/ENGINEERING-LOG.md) records why each constraint exists — F-40 for headless, F-44 for the session key and device trust, F-46 for proxy stickiness.
