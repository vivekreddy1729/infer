Deploying Carrier Policy Puller on Windows EC2

One Windows Server instance running headed Chrome inside an interactive desktop session, behind an Application Load Balancer for TLS. State on EBS. Everything is AWS except the residential proxy, which is Proxy-Cheap.

The one thing that will cost you an afternoon if you skip it

This app cannot run as a Windows Service. Not "should not" — cannot. The reasoning is three facts that combine badly, and it is the first section below. Every normal instinct for running a server on Windows leads to Session 0, and Session 0 is exactly where this app fails.

1. Why it cannot be a Windows Service

Three facts. Each is established independently; the conclusion is forced.

FactEvidence
GEICO requires a headed browser. HEADLESS=false is not a preference. Measured: POST /ws/login/authenticate returns 302 headless and 200 headed on the same credentials. ENGINEERING-LOG F-40.
Headed Chrome needs an interactive desktop — a window station with a real desktop to draw into. Standard Windows behaviour. Without one, Chrome cannot create a browser window and the launch fails or renders nothing.
Windows Services run in Session 0, which has no interactive desktop. So does Task Scheduler with "run whether user is logged on or not", and so does anything wrapped by NSSM, sc.exe, or PM2-as-a-service. Session 0 isolation, standard since Windows Vista.

On Linux this is solved with Xvfb, a virtual framebuffer that hands Chrome a display with no GPU and no monitor. That is what docker-entrypoint.sh does, and it is why the Fargate design works. Windows has no Xvfb and no equivalent.

Therefore: auto-logon, plus Task Scheduler triggered at logon

The process must live in an interactive session (Session 1+). The instance auto-logs-on a dedicated local account at boot, and a scheduled task set to run only when user is logged on starts the app in that session. Steps 5 to 7 below.

This inverts normal Windows server practice, and it is the part of this deployment to prove first — before wiring up load balancers or certificates. A five-minute check (section 8) tells you whether the whole approach holds on your instance.

2. The other three properties that shape the design

Sessions live in memory, and a pull waits on a human

A pull holds an open browser context in an in-memory Map while a person reads a text message and types a code. That context cannot be serialised, so it cannot be shared between instances.

Exactly one instance. This is correctness, not cost control.

No Auto Scaling Group above 1, no second instance for redundancy. With two, a user's WebSocket can land on the instance that is not holding their browser, and the pull hangs at the MFA prompt with no error. Sticky sessions do not rescue this — they pin the socket, not the browser context. Set any ASG to min 1 / max 1 / desired 1, and use it for replacement on failure, never for scaling.

The MFA WebSocket is idle for minutes

ALB idle timeout must exceed MFA_WAIT_TIMEOUT_MS

The default ALB idle timeout is 60 seconds. MFA_WAIT_TIMEOUT_MS is 180 seconds, because that is how long a human plausibly takes. The socket is genuinely idle in that window — nothing is being sent while someone finds their phone.

At the default, the ALB closes the connection mid-wait and the user sees "the connection to this session is closed", which points at the app, the browser, or the carrier. Set it to 300 seconds. Nothing enforces the relationship between these two numbers, so if you raise MFA_WAIT_TIMEOUT_MS, raise this too.

State must survive a restart

Two things persist, and both matter for latency and for MFA frequency:

  • data/sessions/ — encrypted storageState. Lets a repeat pull skip login entirely.
  • data/profiles/ — real on-disk Chrome profiles. These carry GEICO's "remember this device" marker, which is what allows a pull to skip the human MFA round-trip altogether.

EBS makes this simpler than Fargate did

The Fargate design needed EFS, an access point, a uid mapping and a mount target purely to keep these two directories alive across task replacement. On EC2 they are just files on the root volume. One fewer service, one fewer failure mode, and the uid-mapping question disappears.

Real Chrome becomes practical. stealth.js prefers channel: 'chrome' and falls back to bundled Chromium. 5. Sizing and cost

Chrome is the memory consumer, not Node. A headed Chrome with a persistent profile plus the warm-page pool wants real headroom, and Windows Server itself takes more than a Linux base.

ResourceChoiceWhy
AMIWindows Server 2022 BaseHas PowerShell 5.1 and netstat, which tools/restart-server.js uses. No desktop-experience add-on needed.
Instancet3.large (2 vCPU, 8 GiB)t3.medium (4 GiB) is the floor and will work for a single pull, but leaves nothing for a second browser context or a Windows update running concurrently.

ALB1, 2 subnetsTLS termination. An ALB requires two subnets in different AZs even with one target.

Windows licensing is the dominant cost difference

A Windows instance costs materially more per hour than the same Linux instance, because the licence is in the price. Rough order of magnitude for this shape is tens of dollars per month for the instance, plus roughly $16–20/month for the ALB, plus EBS and proxy. These are ballpark figures — price your exact region and instance in the AWS Pricing Calculator rather than trusting a number in a document.

If cost matters more than TLS-at-the-edge convenience, step 9 notes a single-box alternative that drops the ALB.

6. Deployment, step by step

1

Launch the instance

Windows Server 2022 Base, t3.large, gp3 50 GiB. Attach an Elastic IP. Create an IAM instance role with read access to the secret you will create in step 4 (secretsmanager:GetSecretValue scoped to that secret's ARN).

Security groups, tightened now rather than later:

  • ALB SG — inbound 443 from 0.0.0.0/0.
  • Instance SG — inbound 3000 from the ALB SG only, never from the internet. Inbound 3389 (RDP) from your own IP only.

Do not expose 3000 publicly

The app accepts carrier credentials. Without the ALB in front there is no TLS, and those credentials would cross the internet in plaintext.

2

Install Node, Git, and real Chrome

RDP in. Windows Server has no winget by default, so use Chocolatey — or download each MSI by hand if you prefer not to add a package manager. 

# PowerShell as Administrator
Set-ExecutionPolicy Bypass -Scope Process -Force
[System.Net.WebClient]::new().DownloadString('https://community.chocolatey.org/install.ps1') | iex

choco install -y nodejs-lts git googlechrome

# New shell so PATH updates take effect, then confirm
node --version    # must satisfy .nvmrc
git --version

Installing Chrome here is worth doing properly

stealth.js tries channel: 'chrome' first and silently falls back to bundled Chromium. The fallback works but is a weaker anti-detection posture. npm run doctor reports which one is actually in use — check it in step 8.

3

Clone and install

cd C:\
git clone https://github.com/vivekreddy1729/infer.git app
cd C:\app

npm ci
npm run setup      # non-interactive, idempotent; creates data\ logs\ artifacts\
npx patchright install chromium
npx patchright install chrome

npm run setup is safe to re-run. It will not overwrite an existing .env.

4

Put the secrets in Secrets Manager, not in the repo

Create one secret holding the values that must never be committed. Carrier credentials are supplied by the user at runtime through the UI and are not stored here; what belongs here is infrastructure configuration. 

{
  "SESSION_ENCRYPTION_KEY": "<32-byte base64>",
  "RESIDENTIAL_PROXY_URL":  "http://USER:PASS@<proxy-ip>:<port>",
  "PROXY_MODEL":            "dedicated",
  "DIAGNOSTICS_TOKEN":      "<random>"
}

Fetch it at boot and materialise .env:

# C:\app\tools\fetch-secrets.ps1
$json = (Get-SECSecretValue -SecretId carrier-puller/prod).SecretString
$vals = $json | ConvertFrom-Json
$lines = @(
  "NODE_ENV=production",
  "PORT=3000",
  "HEADLESS=false",          # required for GEICO - see section 1
  "PROXY_MODEL=dedicated"
)
foreach ($p in $vals.PSObject.Properties) { $lines += "$($p.Name)=$($p.Value)" }
Set-Content -Path C:\app\.env -Value $lines -Encoding UTF8

Two settings the app enforces or depends on

  • SESSION_ENCRYPTION_KEY — the app hard-fails at boot in production without a valid 32-byte key. That is deliberate: the alternative is silently writing session state you cannot decrypt later.
  • HEADLESS=false — if this drifts to true, Progressive keeps working and GEICO starts failing with a generic sign-in error. See section 9.

Leave the Proxy-Cheap management API key off this machine

PROXYCHEAP_API_KEY and PROXYCHEAP_API_SECRET can order proxies and buy bandwidth. The server never reads them — only npm run proxy:discover and proxy:autoextend do, and those are operator tools. npm run doctor warns if it finds them set with NODE_ENV=production.

5

Configure auto-logon

Create a dedicated local account for the app — do not reuse the built-in Administrator. Then enable auto-logon so a desktop session exists after every reboot.

Use Sysinternals Autologon rather than editing the registry by hand. Both achieve the same thing, but the registry method stores DefaultPassword in plaintext under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon, readable by any local administrator. Autologon puts it in the LSA secrets store instead. 

# Download Autologon from Sysinternals, then:
Autologon64.exe app-runner <domain-or-machine> <password>

# Verify it took (AutoAdminLogon should be 1, and there should be no DefaultPassword value)
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon' |
  Select-Object AutoAdminLogon, DefaultUserName

This is a real security trade, so state it plainly

Auto-logon means the instance boots into a logged-in interactive desktop with no human present. Anyone who reaches the console reaches that desktop. It is accepted here because section 1 leaves no alternative for a headed browser. Compensate by keeping RDP restricted to your own IP, using a dedicated non-administrator-where-possible account, and not putting anything on that desktop beyond this app.

6

Start the app with Task Scheduler, in the interactive session

The trigger is At log on for the app account, and the critical setting is Run only when user is logged on. Choosing "whether user is logged on or not" puts the task in Session 0 and Chrome will not start. 

$action  = New-ScheduledTaskAction `
  -Execute 'C:\Program Files\nodejs\node.exe' `
  -Argument 'src\server.js' `
  -WorkingDirectory 'C:\app'

$trigger = New-ScheduledTaskTrigger -AtLogOn -User 'app-runner'

# Interactive = Session 1+. This is the whole point.
$principal = New-ScheduledTaskPrincipal -UserId 'app-runner' -LogonType Interactive

$settings = New-ScheduledTaskSettingsSet `
  -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) `
  -ExecutionTimeLimit 0 `          # never kill a long-running server
  -MultipleInstances IgnoreNew     # never start a second one

Register-ScheduledTask -TaskName 'CarrierPolicyPuller' `
  -Action $action -Trigger $trigger -Principal $principal -Settings $settings

If you use the fetch-secrets.ps1 from step 4, run it before the server — either as a second action on the same task, or from a small wrapper script that calls it and then starts Node.

-ExecutionTimeLimit 0 and IgnoreNew both matter

The default execution time limit is three days, after which Task Scheduler kills the server. And IgnoreNew prevents a second instance — two servers means one serves while the other idles, and which one you are talking to becomes a coin flip.

7

Keep the desktop alive after you disconnect RDP

This is the sharp edge of the whole approach. Disconnecting an RDP session can leave it without a usable desktop surface, and a headed Chrome in that session may then fail to render. Logging off is worse — it ends the session and kills the app.

The standard remedy is tscon, which redirects your session to the physical console so it stays attached to a real desktop after you disconnect: 

# From an elevated prompt INSIDE the RDP session you are about to leave.
# This disconnects you immediately - that is expected.
query session
tscon <your-session-id> /dest:console

Verify this on your instance before trusting it

Behaviour here varies with Windows build, RDP client, and whether the instance has a console session available. Prove it the boring way: connect, run tscon, disconnect, wait a few minutes, then drive a full pull from outside and confirm the browser still renders. Do that before you rely on the deployment — not during a demo.

If it proves unreliable on your build, the honest fallback is to keep one RDP session connected for the duration of a demo. Ugly, and worth knowing rather than discovering.

8

Restrict the credential-bearing directories with icacls

The code creates data\, logs\ and the diagnostics and metrics stores with mode: 0o700. Node ignores mode on Windows, so those directories simply inherit the parent ACL and nothing reports that the protection is missing.

This is not paranoia about ordinary data. data\profiles\ holds live Chrome profiles: real carrier cookies, and GEICO's device-trust marker. A profile directory is equivalent to a logged-in browser.

icacls C:\app\data /inheritance:r ^
  /grant:r "app-runner:(OI)(CI)F" ^
  /grant:r "Administrators:(OI)(CI)F"

icacls C:\app\data /verify    # confirm the result, do not assume it
9

Load balancer, certificate, and the idle timeout

Request an ACM certificate for your domain. Create an internet-facing ALB across two subnets, an HTTPS :443 listener using that certificate, and a target group pointing at the instance on HTTP :3000 with health check GET /api/health. 

# The setting that is wrong by default
aws elbv2 modify-load-balancer-attributes ^
  --load-balancer-arn <alb-arn> ^
  --attributes Key=idle_timeout.timeout_seconds,Value=300

Then allow 3000 inbound on the instance security group from the ALB security group only, and confirm Windows Firewall is not blocking it: 

New-NetFirewallRule -DisplayName 'CarrierPuller 3000' `
  -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow

Cheaper alternative: skip the ALB and run Caddy on the instance as a reverse proxy on :443. It obtains and renews a Let's Encrypt certificate automatically and proxies WebSockets without extra configuration. You then manage a certificate on the box, and you must set Caddy's own read/write timeouts above 180 seconds for the same reason the ALB needs 300.

7. Proxy-Cheap: why IP whitelisting is now the right choice

Proxy-Cheap offers two authentication modes, and they are mutually exclusive — switching to one revokes the other: 

GET /proxies/{id}/change-authentication-type
{"currentAuthenticationType":"USERNAME_PASSWORD",
 "availableAuthenticationTypes":["IP_WHITELIST","USERNAME_PASSWORD"]}

This target reverses the earlier decision

Whitelisting was rejected for Fargate (OPTIMISATION-LOG O-17) for one reason: a Fargate task gets a new public address every replacement, so a whitelist would break on every deploy, and because the modes are exclusive that locks the proxy out entirely.

An EC2 instance with an Elastic IP does not have that problem. The egress address is fixed across reboots, redeploys and instance stop/start. Every objection in O-17 was conditional on a moving address, and here it does not move — so the reasoning inverts and whitelisting becomes the better posture. It removes the proxy password from the instance entirely, so a compromised box leaks nothing reusable.

Sequence, and the order matters:

  1. Attach the Elastic IP and confirm the actual egress address as the app sees it: curl https://api.ipify.org from the instance. Use that value, not the EIP from the console, in case anything NATs in between.
  2. Register it: POST /proxies/{id}/whitelist-ip with {"ips":["<eip>"]}.
  3. Switch mode: POST /proxies/{id}/change-authentication-type with {"newAuthType":"IP_WHITELIST","ips":["<eip>"]}.
  4. Strip the credentials from RESIDENTIAL_PROXY_URL, leaving http://<proxy-ip>:<port>.
  5. Re-run npm run proxy:verify before spending a real carrier login.

It is a one-way door, so have the key pair to hand

If the whitelisted address is wrong, the proxy stops answering and the only route back is the management API — the credential deliberately kept off this machine. Do this from your laptop, not from the instance, and confirm proxy:verify passes before removing the password.

Unrelated to auth, and it will bite on a schedule

All three proxies on the account have autoExtendEnabled: true, which looks like protection. Account balance is 0. Auto-extend renews by charging balance, so it will fail on the day it runs and the exit IP will disappear between pulls. npm run proxy:verify now fails specifically on that combination and distinguishes it from a routing fault. Top up before the expiry date it prints.

Also keep PROXY_MODEL=dedicated and PROXY_USERNAME_TEMPLATE unset. The account holds RESIDENTIAL_STATIC proxies — one fixed exit IP each, no session concept. A username template would rewrite a username the provider expects verbatim, and the resulting auth failure looks exactly like a blocked IP (F-52).

8. Verifying the deployment

In this order. Each step proves one thing, so a failure localises immediately.

Do step 1 before building any of the AWS plumbing

It tests the assumption the entire design rests on. If a headed Chrome cannot render in your auto-logon session, no amount of load balancer configuration helps.

#CheckProves
1 Reboot. Do not RDP in. From your laptop: curl http://<eip>:3000/api/health (temporarily allow your IP), then drive a full GEICO pull. Auto-logon produced a real desktop, Task Scheduler started the app in it, and headed Chrome rendered with nobody logged in. This is the load-bearing check.
2 npm run doctor Node version, .env present, valid SESSION_ENCRYPTION_KEY, HEADLESS=false, proxy configured, and whether real Chrome or bundled Chromium is in use. Expect zero warnings except possibly the port-in-use note.
3 npm run proxy:verify Traffic actually leaves via the proxy and holds one IP across a window longer than a pull. Also fails loudly on the auto-extend/zero-balance combination.
4 npm run smoke:all 202 checks against the built-in demo portal, end to end over the real transport. Loopback is in PROXY_BYPASS, so this spends no metered proxy bandwidth.
5 curl https://<domain>/api/health through the ALB Certificate, listener, target group and both security groups.
6 A real pull through the ALB, and wait at least 90 seconds at the MFA prompt before entering the code. The idle timeout. At the 60-second default this is exactly where it fails, and a fast tester never sees it.
7 Run the same pull twice. Session reuse. The second should report a warm path and skip login — proving data\ persisted and the ACLs did not lock the app out of its own directory.
8 Open any page and read the egress badge. The browser's real exit IP, not the host's. It should match the Proxy-Cheap address.

10. Logs, reboots, and day-two operations

Getting logs out

logs\server.log is rotated by the app. To read it without RDP, install the CloudWatch Agent and ship that file; the IAM instance role needs logs:CreateLogStream and logs:PutLogEvents.

The app also writes a redacted diagnostic bundle per failure to logs\failures\. Those are safe to share — credentials, codes, cookies and tokens are redacted at the logger — and they are the fastest way to diagnose a carrier-side failure. F-53 was found by noticing which API call was missing from one.

Never attach a Chrome profile to a bug report

data\profiles\ contains live session cookies, and Chrome records visited URLs in its history and session-restore files — which includes the carrier OAuth token that arrives in a URL fragment. Nothing the app writes puts it there; Chrome does. Diagnostic bundles never include profile contents, which is what keeps them shareable.

Reboots

A reboot is the routine path and should need no intervention: auto-logon creates the session, the scheduled task starts the app, and data\ on EBS preserves both the encrypted session store and the Chrome profiles, so device trust survives. The one thing a reboot does not restore is the tscon redirection — re-verify with check 1 after the first reboot rather than assuming.

Updating the deployment

cd C:\app
git pull
npm ci
npm run restart      # verifies the old process actually died
npm run doctor
npm run smoke:all

npm run restart is Node rather than shell specifically so it works here — the previous implementation needed lsof, pkill, pgrep, ps, find -newermt, curl and python3, none of which exist on a stock Windows Server image (F-55). It identifies the server by who holds the port, confirms exactly one is running, and checks no source file is newer than the running process — the failure that caused F-38.

Windows Update

Automatic reboots will interrupt a pull

A pull holds an in-memory session and an open browser context; a reboot mid-pull loses it. With a single instance there is nowhere to drain to. Set Windows Update to a fixed maintenance window outside demo hours, and treat an update reboot as a deliberate action rather than something the instance decides on its own.
